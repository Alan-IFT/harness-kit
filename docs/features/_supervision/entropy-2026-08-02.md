## Detail

### EP-001 — two review roles name an output their tool grant cannot produce

`agents/gate-reviewer.md:4` and `agents/code-reviewer.md:4` both declare `tools: Read, Glob, Grep`.
Both `## What you produce` sections nonetheless open with **"The contract portion —
`docs/features/<task-slug>/03_GATE_REVIEW.md`"** / **`05_CODE_REVIEW.md`** (`:14` in each), instruct
the agent to "correct this document **in place**" on a re-review round (`gate-reviewer.md:29`,
`code-reviewer.md:31`), and describe a `0N_RATIONALE.md` sibling "written **only when non-empty**"
(`:32`, `:36`). None of those verbs is reachable without a `Write` tool.

The reconciliation exists in exactly one of the three contracts that must implement it, as a
parenthetical: `gate-reviewer.md:36-37` — *"(You are read-only: if you have no `Write` tool, return
both portions in your final message and the PM persists them verbatim.)"*. `code-reviewer.md`
carries no equivalent anywhere. And the agent that actually performs the write does not carry it at
all: `pm-orchestrator.md:30,32` attributes both files to the two reviewers in its stage table and
states no persist obligation — the PM's contract states such a duty only for the round record into
`PM_LOG.md` (`:86`).

This is the leak: the *tool grant* of the callee — an implementation detail of the agent
declaration — determines an obligation of the caller, and the caller's interface does not name it.
It is not hypothetical. `.harness/insight-index.md:54-61` records it fired during T-22, with three
documents (`03_GATE_REVIEW.md`, `05_CODE_REVIEW.md`, `05_RATIONALE.md`) persisted by the PM on the
reviewers' behalf, and notes the condition is "latent for as long as both contracts have named an
output they cannot produce".

Two deepenings are available and the scan does not pick between them: widen the two tool grants
(removing the seam), or state the persist duty once in the PM stage table (giving the seam one
owner, in the file the writer reads). Either concentrates; the present arrangement is one and a half
statements spread across three contracts.

### EP-002 — the standing operator ledger has no module, so it squats in the baseline pin file

`.harness/scripts/baseline.json` is 31 lines. Lines 2–24 are the twenty scalar keys the file exists
for. Lines 25–29 are five `_qa_note_t{20,17,13,16,12}` string values carrying human-readable prose —
24,874 characters of it, as measured at `docs/proposals/operator-powershell-checklist.md:127`.

Nothing reads those values mechanically. `verify_all.sh:852` touches the file only as a G.4
count-claim site; `agents/qa-tester.md:83` sends the QA stage to it "for current test counts and
metrics" (`:88` writes them back). So every consumer of the twenty numbers loads ~25 KB of narrative
to reach them.

The prose is not filler, which is what makes this a deepening candidate rather than a deletion. It
is the sole home of the standing PowerShell operator obligations — `pwsh` is not installed on the
development host, so every `.ps1` edit ships green-by-symmetry only. `_qa_note_t16` states "total
standing operator obligations go 19 -> 24"; `_qa_note_t20` adds numbered item 17. By the notes' own
arithmetic that is **17 numbered plus 8 un-numbered (`_qa_note_t13`) = 25** obligations that gate a
release, held as prose inside a machine-read pin file, with no add/close operation and nothing
enforcing that the count is current.

A second home appeared during this wave and has already drifted. `docs/proposals/operator-powershell-checklist.md`
is self-described as "a convenience index, not a new source of truth ... where this summary and a
note disagree, the note wins" (`:4-6`). Its `## Standing count` reads "**17 numbered items, 4 marked
security-relevant**" (`:32`), and its origin table maps `_qa_note_t13` to "refines 3, 6, 8" (`:38`).
But `_qa_note_t13`'s "it widens items 3, 6 and 8" names that note's own local indices among its
**8 un-numbered obligations** — which the checklist's count then omits entirely. One day old, two
homes, already 8 of 25 obligations apart. The checklist's own `## A structural note` (`:123-131`)
reaches the same conclusion unprompted and declines to act on it.

The deepening is a ledger with its own interface (an obligation has an id, an origin, a
security flag, and an open/closed state) so the pin file returns to pinning numbers and the count
stops being a hand-summed claim. Deleting the prose is not an option — that is precisely the signal.

### EP-003 — the live check count leaks into 12 documents behind a hand-enumerated allowlist

`verify_all.sh` derives its own check count at run time, then G.4 asserts that a fixed list of
**11** documents restates it correctly (`:841-878`, arrays `g4_files` / `g4_shapes` / `g4_expects`).
The mechanism is sound and deliberately reasoned — its own comment at `:838-840` records a prior
hazard within it (the test is whole-file, so each row's `expect` must be unique inside its file or a
sibling line silently masks drift) — but it closes by enumeration, not by construction.

`CONTRIBUTING.md:22` states *"the gate currently runs 32 checks"*. It appears in no `g4_files` entry
and is referenced by no `.sh` or `.ps1` in the repository. It happens to read 32 today, so there is
**no live drift** — the finding is that a twelfth restatement of the number sits outside the gate,
which is what a hand-maintained allowlist over a leaking fact produces. The other eleven sites are
`AI-GUIDE.md:74`, `.harness/rules/40-locations.md:29`, `docs/dev-map.md:87,187`, `README.md` (badge
+ prose), `README.zh-CN.md` (badge + prose), `docs/manual-e2e-test.md`, and `baseline.json:10`.

The deepening is the move T-16 has just applied to the hook byte-forms: derive the site set rather
than carry it — scan for the shape and assert every hit — so a new document mentioning the count is
gated on arrival instead of on someone remembering to extend an array. Strength is
`Worth exploring` rather than `Strong` because the current mechanism does catch the eleven it
knows, and the twelfth is presently in agreement.
